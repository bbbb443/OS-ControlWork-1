## Вихідні транзакції

```text
T1 = W[D] W[A] W[B] A1
T2 = R[D] R[A] W[D] C2
T3 = W[B] R[A] W[D] C3
```

## Завдання 2. Історія виконання

Для цієї історії я використала протокол блокування 2-го ступеня. Перед читанням транзакція отримує S-блокування і знімає його після читання. Перед записом вона отримує X-блокування та утримує його до Commit або Abort. Два S-блокування сумісні між собою, а X-блокування не допускає S- або X-блокувань інших транзакцій на той самий елемент.

У таблиці я використала такі позначення: S_i(Z) — спільне блокування, X_i(Z) — виключне блокування, U_i(Z) — зняття блокування. Індекс i позначає номер транзакції. request означає запит на блокування, а wait — очікування його отримання.

| Крок | T1 | T2 | T3 |
|---:|---|---|---|
| 1 | X1(D) | | |
| 2 | W1[D] | | |
| 3 | | request S2(D); wait через X1(D) | |
| 4 | X1(A) | | |
| 5 | W1[A] | | |
| 6 | X1(B) | | |
| 7 | W1[B] | | |
| 8 | | | request X3(B); wait через X1(B) |
| 9 | A1: відкат усіх змін T1 | | |
| 10 | U1(D), U1(A), U1(B) після відкату | | |
| 11 | | Надання S2(D), завершення очікування | |
| 12 | | R2[D] | |
| 13 | | U2(D) | |

Я склала історію так, щоб операції трьох транзакцій чергувалися, але їхній порядок усередині кожної транзакції залишався таким, як в умові. Спочатку T1 блокує D, тому T2 очікує. Потім T3 також переходить до очікування через блокування B. Після A1 зміни T1 відкочуються, блокування знімаються, і T2 та T3 можуть продовжити роботу.

Далі T3 очікує звільнення D транзакцією T2. Після C2 вона отримує блокування, виконує запис і завершується через C3. Отже, виконання частково успішне: T1 скасована, а T2 і T3 зафіксовані. T2 читає D та A вже після відкату T1.

## Завдання 3. Таблиця блокувань і граф очікування

Таблицю блокувань я склала для моменту після кроку 24, перед першою фіксацією C2. На цей момент T1 уже скасована, T2 утримує X(D), а T3 утримує X(B) та очікує X(D). У set_locks я записала отримані блокування, у wait_locks — ті, на які транзакція очікує. Порожні рядки означають, що блокувань немає.

```c
const char *lock_table[][3] = {
    /* name, set_locks, wait_locks */
    { "T1", "",     ""     }, /* aborted */
    { "T2", "X(D)", ""     },
    { "T3", "X(B)", "X(D)" }
};

/* Ребро: хто очікує -> хто утримує блокування. */
const char *wait[][2] = {
    { "T3", "T2" }
};
```

За цим станом я отримала граф **T3 → T2**. Стрілка показує, що T3 очікує на T2. Циклу немає, тому deadlock відсутній. T2 може виконати Commit і звільнити D, після чого T3 продовжить роботу.

Також я навела стан після кроку 8, щоб показати очікування до скасування T1:

```c
const char *lock_table_before_abort[][3] = {
    { "T1", "X(D), X(A), X(B)", ""     },
    { "T2", "",                 "S(D)" },
    { "T3", "",                 "X(B)" }
};

const char *wait_before_abort[][2] = {
    { "T2", "T1" },
    { "T3", "T1" }
};
```

У цьому випадку я отримала два ребра: T2 → T1 і T3 → T1. Циклу знову немає, оскільки сама T1 ні на кого не очікує. Вона виконує Abort і звільняє блокування. Отже, у складеній історії взаємного блокування немає.

## Завдання 4. SQL-команди встановлення блокувань

Для SQL-команд я обрала **Microsoft SQL Server**, оскільки в умові СУБД не вказана. Назви таблиць — dbo.A, dbo.B та dbo.D. Припускаю, що це звичайні дискові таблиці, а параметр **READ_COMMITTED_SNAPSHOT вимкнений (OFF)**. За такої умови читання на рівні READ COMMITTED використовує S-блокування.

Кожну транзакцію потрібно виконувати в окремому з’єднанні. Перед її операціями я передбачила такі команди:

```sql
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
BEGIN TRANSACTION;
```

Нижче я зіставила запити на блокування з SQL-командами. Їхній порядок відповідає таблиці історії. Якщо ресурс зайнятий, команда очікує на його звільнення.

| Крок запиту | Блокування | SQL-команда |
|---:|---|---|
| 1 | X1(D) | `SELECT * FROM dbo.D WITH (TABLOCKX, XLOCK);` |
| 3 | S2(D), очікування до 11 | `SELECT * FROM dbo.D WITH (TABLOCK, READCOMMITTED);` |
| 4 | X1(A) | `SELECT * FROM dbo.A WITH (TABLOCKX, XLOCK);` |
| 6 | X1(B) | `SELECT * FROM dbo.B WITH (TABLOCKX, XLOCK);` |
| 8 | X3(B), очікування до 14 | `SELECT * FROM dbo.B WITH (TABLOCKX, XLOCK);` |
| 16 | S2(A) | `SELECT * FROM dbo.A WITH (TABLOCK, READCOMMITTED);` |
| 19 | X2(D) | `SELECT * FROM dbo.D WITH (TABLOCKX, XLOCK);` |
| 21 | S3(A) | `SELECT * FROM dbo.A WITH (TABLOCK, READCOMMITTED);` |
| 24 | X3(D), очікування до 27 | `SELECT * FROM dbo.D WITH (TABLOCKX, XLOCK);` |

Для S-блокування таблиці я використала TABLOCK під час SELECT. Після читання це блокування знімається. Для X-блокування я використала TABLOCKX разом із XLOCK, щоб утримувати його до завершення транзакції.

SELECT із цими X-підказками лише встановлює блокування. Для самих операцій W потрібні окремі команди зміни даних. Їх я не розписувала, оскільки в умові немає структури таблиць і значень для запису. Читання та зняття S-блокування, які я показала окремими кроками в історії, відбуваються під час виконання відповідного SELECT.

Для завершення транзакцій я використала такі команди:

```sql
-- З’єднання T1, крок 9:
ROLLBACK TRANSACTION;

-- З’єднання T2, крок 25:
COMMIT TRANSACTION;

-- З’єднання T3, крок 29:
COMMIT TRANSACTION;
```

Після ROLLBACK або COMMIT X-блокування знімаються автоматично. Тому окрему команду зняття блокувань я не додавала.
