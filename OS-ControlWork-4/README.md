## Вихідні транзакції

```text
T1 = W[D] W[A] W[B] A1
T2 = R[D] R[A] W[D] C2
T3 = W[B] R[A] W[D] C3
```

## Завдання 2. Історія виконання

Протокол блокування 2-го ступеня: перед читанням встановлюється S-блокування, яке можна зняти після читання; перед записом встановлюється X-блокування, яке утримується до Commit або Abort. S сумісне із S; X несумісне з S та X іншої транзакції. Ступінь блокування не слід плутати з двофазним протоколом.

Позначення: S_i(Z), X_i(Z) — надання спільного або виключного блокування Z транзакції Ti; U_i(Z) — зняття блокування; request — запит; wait — очікування. Запит, що очікує, ще не є наданим блокуванням.

| Крок | T1 | T2 | T3 |
|---:|---|---|---|
| 1 | X1(D) | | |
| 2 | W1[D] | | |
| 3 | | request S2(D); wait через X1(D) | |
| 4 | X1(A) | | |
| 5 | W1[A] | | |
| 6 | X1(B) | | |
| 7 | W1[B] | | |
| 8 | | | request X3(B); wait через X1(B) |
| 9 | A1: відкат усіх змін T1 | | |
| 10 | U1(D), U1(A), U1(B) після відкату | | |
| 11 | | Надання S2(D), завершення очікування | |
| 12 | | R2[D] | |
| 13 | | U2(D) | |
| 14 | | | Надання X3(B), завершення очікування |
| 15 | | | W3[B] |
| 16 | | S2(A) | |
| 17 | | R2[A] | |
| 18 | | U2(A) | |
| 19 | | X2(D) | |
| 20 | | W2[D] | |
| 21 | | | S3(A) |
| 22 | | | R3[A] |
| 23 | | | U3(A) |
| 24 | | | request X3(D); wait через X2(D) |
| 25 | | C2 — перша фіксація змін | |
| 26 | | U2(D) | |
| 27 | | | Надання X3(D), завершення очікування |
| 28 | | | W3[D] |
| 29 | | | C3 |
| 30 | | | U3(B), U3(D) |

Історія квазіпаралельна: операції транзакцій чергуються. Вона частково успішна: T1 скасовано згідно із заданою A1, а T2 і T3 зафіксовано. Порядок початкових операцій кожної транзакції збережено. T2 читає D та A після завершення відкату T1, тому не читає її незафіксованих змін. Усі X-блокування знімаються лише після завершення відповідної транзакції.

## Завдання 3. Таблиця блокувань і граф очікування

Основний знімок: після кроку 24, безпосередньо перед першою фіксацією C2 на кроці 25. Колонки: name — транзакція; set_locks — надані блокування; wait_locks — запити в очікуванні. Порожній рядок означає відсутність блокувань.

```c
const char *lock_table[][3] = {
    /* name, set_locks, wait_locks */
    { "T1", "",     ""     }, /* aborted */
    { "T2", "X(D)", ""     },
    { "T3", "X(B)", "X(D)" }
};

/* Ребро: хто очікує -> хто утримує блокування. */
const char *wait[][2] = {
    { "T3", "T2" }
};
```

Граф: **T3 → T2**. Циклу немає, отже deadlock відсутній. T2 може виконати C2 та звільнити D, після чого T3 продовжить виконання.

Для відображення попередніх очікувань наведено додатковий знімок після кроку 8, перед A1:

```c
const char *lock_table_before_abort[][3] = {
    { "T1", "X(D), X(A), X(B)", ""     },
    { "T2", "",                 "S(D)" },
    { "T3", "",                 "X(B)" }
};

const char *wait_before_abort[][2] = {
    { "T2", "T1" },
    { "T3", "T1" }
};
```

Тут граф має ребра T2 → T1 та T3 → T1. Циклу також немає: T1 не очікує й виконує передбачений умовою Abort. Протягом усієї історії deadlock не виникає.

## Завдання 4. SQL-команди встановлення блокувань

СУБД в умові не зазначена. Нижче обрано **Microsoft SQL Server**, звичайні дискові таблиці dbo.A, dbo.B, dbo.D та навчальну БД із параметром **READ_COMMITTED_SNAPSHOT OFF**. Це суттєва передумова: у такій конфігурації READ COMMITTED використовує S-блокування, а не версії рядків.

Кожна транзакція виконується в окремому з’єднанні. На початку кожної:

```sql
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
BEGIN TRANSACTION;
```

Виконувати команди у порядку історії; заблокована команда продовжується після звільнення потрібного ресурсу.

| Крок запиту | Блокування | SQL-команда |
|---:|---|---|
| 1 | X1(D) | `SELECT * FROM dbo.D WITH (TABLOCKX, XLOCK);` |
| 3 | S2(D), очікування до 11 | `SELECT * FROM dbo.D WITH (TABLOCK, READCOMMITTED);` |
| 4 | X1(A) | `SELECT * FROM dbo.A WITH (TABLOCKX, XLOCK);` |
| 6 | X1(B) | `SELECT * FROM dbo.B WITH (TABLOCKX, XLOCK);` |
| 8 | X3(B), очікування до 14 | `SELECT * FROM dbo.B WITH (TABLOCKX, XLOCK);` |
| 16 | S2(A) | `SELECT * FROM dbo.A WITH (TABLOCK, READCOMMITTED);` |
| 19 | X2(D) | `SELECT * FROM dbo.D WITH (TABLOCKX, XLOCK);` |
| 21 | S3(A) | `SELECT * FROM dbo.A WITH (TABLOCK, READCOMMITTED);` |
| 24 | X3(D), очікування до 27 | `SELECT * FROM dbo.D WITH (TABLOCKX, XLOCK);` |

TABLOCK при читанні задає спільне блокування всієї таблиці. У вибраному режимі S-блокування знімаються після читання. TABLOCKX задає виключне блокування таблиці; XLOCK утримує його до завершення транзакції. SELECT з X-підказками використано як команду встановлення блокування; самі W-операції виконуються окремими UPDATE/INSERT/DELETE. Конкретні зміни даних не наведено, бо умова не містить структури таблиць та значень. Кроки читання та зняття S-блокувань у теоретичній історії деталізують виконання відповідного SELECT.

Завершення транзакцій:

```sql
-- З’єднання T1, крок 9:
ROLLBACK TRANSACTION;

-- З’єднання T2, крок 25:
COMMIT TRANSACTION;

-- З’єднання T3, крок 29:
COMMIT TRANSACTION;
```

Після ROLLBACK або COMMIT СУБД автоматично знімає X-блокування. Окремої команди UNLOCK у цьому варіанті немає.
